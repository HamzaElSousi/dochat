# Domain Pitfalls

**Domain:** RAG chatbot pipeline on SiteGround shared hosting (Passenger WSGI + ChromaDB + OpenRouter)
**Project:** DocChat RAG Pipeline
**Researched:** 2026-05-07

---

## Critical Pitfalls

Mistakes that cause rewrites, data corruption, or complete service failure.

---

### Pitfall 1: ChromaDB "database is locked" Under Concurrent Requests

**What goes wrong:** ChromaDB uses SQLite under the hood. SQLite permits only one writer at a time. When two HTTP requests arrive simultaneously — one writing (document upload/indexing) and one reading (query) — one of them hits `SQLITE_BUSY`. Without WAL mode and a busy timeout, this surfaces as a 500 error or silent data corruption during indexing.

**Why it happens:** Passenger on shared hosting can spawn multiple worker threads (or be configured to allow concurrent requests) while the ChromaDB `PersistentClient` instance holds open connections to a single SQLite file. The default SQLite journal mode is DELETE, which uses exclusive locks even on reads during active writes.

**Consequences:** Intermittent 500 errors during upload/query overlap. Worst case: partial index writes that corrupt the vector store, requiring a full re-index.

**Prevention:**
- Enable WAL mode on the underlying SQLite connection at application startup: `PRAGMA journal_mode=WAL;`
- Set a busy timeout of at least 5–10 seconds: `PRAGMA busy_timeout=10000;`
- Separate write operations (indexing) from the HTTP request cycle — queue uploads and process them synchronously in a background-safe way. For v1 at <100 queries/day this can be as simple as a file-based task queue processed on the next request.
- Set Passenger to single-process mode (`PassengerMaxPoolSize 1` or equivalent in `.htaccess`) to eliminate true parallelism at the cost of throughput — acceptable at this scale.

**Detection:** Look for `sqlite3.OperationalError: database is locked` in application logs. Enable ChromaDB debug logging during development to surface these early.

**Phase to address:** Phase 1 (Infrastructure / Vector Store setup) — configure WAL mode before any production traffic.

### Pitfall 2: sentence-transformers OOM Kills the Passenger Process

**What goes wrong:** Loading `all-MiniLM-L6-v2` requires approximately 420 MB of RAM. On SiteGround shared hosting, CloudLinux enforces per-user memory limits (PMEM). Loading the model on startup consumes the bulk of the memory budget before any requests arrive. When a large PDF is processed and embeddings are generated in-process, peak memory spikes 2–3x the base model footprint, triggering a CloudLinux OOM kill. The Passenger watchdog then restarts the process, which re-loads the model, which OOM kills again — a restart loop.

**Why it happens:** SiteGround runs CloudLinux with LVE (Lightweight Virtual Environment) hard limits per account. Shared hosting plans typically enforce 512 MB–1 GB PMEM. A model at 420 MB + FastAPI runtime + ChromaDB + request processing overhead leaves almost no headroom.

**Consequences:** 502 Bad Gateway during embedding operations. Server appears to work until first document upload.

**Prevention:**
- Use OpenRouter's embedding endpoint (e.g., `text-embedding-ada-002` via the API) instead of loading sentence-transformers locally. This eliminates the model from RAM entirely.
- If a local model is required: use `paraphrase-MiniLM-L3-v2` (~33 MB) or Model2Vec-distilled variants. Avoid `all-mpnet-base-v2` (420 MB) or any 1B+ parameter model.
- Process embeddings in small batches (8–16 texts at a time) and del/gc intermediates between batches.
- If OOMs persist after optimization: activate the VPS fallback. This is the single most likely reason to leave SiteGround.

**Detection:** Check CloudLinux error logs (`~/logs/` or cPanel Error Log) for `killed` or `Memory limit reached` entries. Monitor process RSS with `ps aux` via SSH after a document upload.

**Phase to address:** Phase 1 (Infrastructure) — validate memory budget before committing to local embeddings. Decide API vs. local embedding at the start, not after an OOM in production.

### Pitfall 3: Embedding Model Mismatch Between Index Time and Query Time

**What goes wrong:** Documents are indexed using model A. At some point the embedding model is changed (upgrade, swap to API) and new documents are indexed with model B. Existing vectors in ChromaDB were generated by model A's geometry. Querying with model B produces cosine distances that are meaningless across the two sets of vectors. Retrieval fails silently — returning wrong or zero results — but the LLM still produces an answer from whatever was retrieved.

**Why it happens:** Developers swap models mid-project without re-indexing the entire collection. Or they embed documents with a local sentence-transformers model and query with the OpenRouter embedding API, not realising the two models produce incompatible vector spaces.

**Consequences:** Silent retrieval degradation. The chatbot answers fluently but from wrong context, causing hallucinations that are hard to attribute to a retrieval failure.

**Prevention:**
- Store the embedding model name and version as metadata in ChromaDB's collection settings at creation time.
- On startup, assert that the configured embedding model matches what was used to create the collection. Abort with a clear error if they differ.
- When changing embedding models: create a new ChromaDB collection and re-index all documents before switching traffic.
- Document the model name in a `.env` variable that is the single source of truth for both indexing and querying paths.

**Detection:** Run a sanity check query after every model change: embed a known phrase and verify the top-1 result is the expected document. A retrieval accuracy below ~70% on known questions is a strong signal.

**Phase to address:** Phase 2 (RAG Pipeline) — enforce the assertion at collection creation time before any documents are ingested.

### Pitfall 4: Fixed-Size Chunking Splitting Logical Units

**What goes wrong:** Naive character or token-count chunking splits a paragraph or a table mid-sentence, or separates a question from its answer. The two halves of the logical unit end up in separate chunks with embeddings that don't independently represent the full concept. Retrieval returns one half without the other. The LLM generates an incomplete or incorrect answer.

**Why it happens:** Fixed-size chunking (e.g., every 500 tokens) is the default in many tutorials. It is fast and simple but oblivious to document structure.

**Consequences:** Increased hallucination rate. The LLM is confident (it received _some_ context) but the context is incomplete.

**Prevention:**
- Use sentence-boundary or paragraph-boundary splitting as the baseline. LangChain's `RecursiveCharacterTextSplitter` with `["\n\n", "\n", ". "]` separators degrades gracefully.
- Target 256–512 tokens per chunk for general prose. Tables and code blocks should be kept as atomic chunks regardless of size.
- Add chunk overlap (10–15% of chunk size) to preserve context across boundaries.
- For PDFs with detectable section headers, use header-aware splitting to keep sections together.

**Detection:** Manually inspect 10 random chunks from an indexed document. If a chunk starts mid-sentence or ends mid-thought, the splitter parameters need tuning.

**Phase to address:** Phase 2 (RAG Pipeline / Document Ingestion) — define and test the chunking strategy before building the query path.

### Pitfall 5: CORS Misconfiguration Blocking the Embeddable Widget

**What goes wrong:** The FastAPI backend is deployed on `api.social-automate.com`. The script-tag widget makes `fetch()` calls from `client-site.com`. Without explicit CORS headers, the browser blocks all widget API calls with a CORS error. The widget appears to load but every chat message fails silently or shows a vague error.

**Why it happens:** FastAPI's `CORSMiddleware` defaults to no allowed origins. Developers test locally (same origin) and miss the cross-origin case until the widget is embedded on an external site.

**Consequences:** Widget completely non-functional on client sites. The error is invisible to the site owner and only visible in the browser console.

**Prevention:**
- Configure `CORSMiddleware` with `allow_origins=["*"]` for a publicly embeddable widget, or maintain an allowlist of authorized embedding domains.
- Set `allow_methods=["GET", "POST"]` and `allow_headers=["Content-Type", "Authorization"]` explicitly.
- Add CORS headers to error responses too — a 422 or 500 without CORS headers also gets blocked by the browser, hiding the real error.
- Test widget embedding on a separate local HTML file served from a different port (e.g., `http://localhost:9000`) before deployment.

**Detection:** Open browser DevTools Network tab. Any `fetch` call to the API returning a CORS error will show `Access-Control-Allow-Origin` missing from the response headers.

**Phase to address:** Phase 3 (Widget / Frontend) — configure CORS in the first API endpoint and test cross-origin in the same phase.

### Pitfall 6: Client Site CSP Blocking the Widget Script

**What goes wrong:** Many WordPress sites and security-hardened sites set a `Content-Security-Policy` header that restricts which scripts can execute and which origins `fetch()` can contact. The widget's `<script>` tag loads from `social-automate.com`, which may be blocked by `script-src 'self'`. The API calls are blocked by `connect-src 'self'`.

**Why it happens:** CSP is managed by the client site, not by the widget author. There is nothing the widget can do server-side to override the client's CSP. This is a documentation and deployment problem, not a code problem.

**Consequences:** Widget silently fails on security-conscious client sites. No error visible to the site owner without checking the browser console.

**Prevention:**
- Document clearly in the widget installation guide that clients must add `social-automate.com` to their `script-src` and `connect-src` CSP directives.
- Provide a copy-paste CSP snippet for common platforms (WordPress with Headers & Footers, Cloudflare, Vercel).
- Consider offering an iframe embed option as an alternative — iframes do not inherit the parent page's CSP for their own content, though they require the host to allow framing via `Content-Security-Policy: frame-ancestors`.

**Detection:** Check the browser console for `Refused to load script` or `Refused to connect` errors mentioning `Content-Security-Policy`.

**Phase to address:** Phase 3 (Widget) — write the installation guide and test against a WordPress site with default Wordfence or iThemes Security CSP rules active.

## Moderate Pitfalls

---

### Pitfall 7: OpenRouter Free Model Rate Limits (50 req/day Without Credits)

**What goes wrong:** OpenRouter free model variants (IDs ending in `:free`) are limited to 20 requests/minute and 50 requests/day if the account has fewer than 10 credits purchased. At launch this ceiling may be hit before the end of the day even with <100 queries/day if the counter resets at UTC midnight and usage is front-loaded.

**Why it happens:** The 50/day limit is a soft default for accounts with no credit balance. Purchasing $10 of credits raises this to 1000/day — but the project plans to use free tier only.

**Consequences:** Users receive API errors after the daily quota is exhausted. The chatbot returns errors for the rest of the day.

**Prevention:**
- Purchase the minimum $10 credit load to move to the 1000/day tier. At free model usage, these credits are not spent; the purchase just unlocks the higher rate limit.
- Implement retry logic with exponential backoff on 429 responses.
- Log every API call with a timestamp. Alert (even via email) when daily usage approaches 80% of quota.
- Configure the `openrouter/free` router as a fallback — it automatically selects an available free model if the primary model is rate-limited or down.

**Detection:** Log all OpenRouter API responses. A `429 Too Many Requests` with the error body mentioning `rate limit` indicates quota exhaustion.

**Phase to address:** Phase 2 (RAG Pipeline / LLM Integration) — implement retry and quota logging before launch.

### Pitfall 8: OpenRouter Free Model Deprecation or Availability Loss

**What goes wrong:** Free model availability on OpenRouter changes without notice. A model that worked last week may be removed, paused, or have its free tier revoked, causing all queries to fail with a 404 or model-not-found error.

**Why it happens:** Free model providers control their own availability. OpenRouter is a routing layer and cannot guarantee indefinite free access to any specific model.

**Consequences:** All chatbot queries fail until the model ID is updated in code and redeployed.

**Prevention:**
- Never hardcode a single model ID. Store it in `.env` as `OPENROUTER_MODEL`.
- Implement a fallback list: `[primary_model, fallback_model_1, fallback_model_2]`. Try each in sequence on failure.
- Subscribe to OpenRouter's status page or changelog for model availability updates.
- The `openrouter/free` auto-router is the simplest fallback: it picks any available free model that matches the request's capability requirements.

**Detection:** A `404` or `{"error": "model not found"}` response from OpenRouter. Log model IDs in every request so failures are immediately diagnosable.

**Phase to address:** Phase 2 — build the fallback list at initial integration, not after the first outage.

### Pitfall 9: Passenger Working Directory and Relative Path Failures

**What goes wrong:** The Passenger WSGI process sets the working directory to the application root at startup. If any code uses relative paths (e.g., `open("data/uploads/file.pdf")` or ChromaDB's `path="./chroma_db"`), those paths resolve correctly in development but break in Passenger because cwd may differ from the script's directory.

**Why it happens:** Passenger's working directory is not guaranteed to be the same as the directory containing `passenger_wsgi.py`. The exact cwd depends on how cPanel's Python Selector invokes the process.

**Consequences:** `FileNotFoundError` on upload or ChromaDB initialization. Application may start successfully but fail on first file access.

**Prevention:**
- Use `pathlib.Path(__file__).parent` as the base for all file paths. Derive all paths from this anchor, never from `os.getcwd()`.
- Set ChromaDB's persist directory to an absolute path computed from `__file__`.
- Add a startup health check that verifies critical directories exist and are writable.

**Detection:** Works in `python app.py` local dev but fails in Passenger. The error log will show `FileNotFoundError` with a path that looks almost right but starts from the wrong root.

**Phase to address:** Phase 1 (Infrastructure) — establish the path convention before any file I/O is written.

### Pitfall 10: pip Install Failures for Native Extension Packages

**What goes wrong:** Packages like `pdfplumber` (depends on `pdfminer.six`), `python-docx`, and `sentence-transformers` require compilation of C/C++ extensions on install. SiteGround's shared hosting may lack `gcc`, `g++`, or system headers (`python3-dev`) in the paths accessible during `pip install`. The install fails with `error: command 'gcc' failed`.

**Why it happens:** Shared hosting restricts access to system-level build tools. CloudLinux jails limit what build tools are visible to the user's pip environment.

**Consequences:** Key dependencies cannot be installed, blocking the entire project.

**Prevention:**
- Prefer pure-Python packages where possible: `pypdf` (pure Python) over `pdfplumber` for basic extraction; `httpx` or `requests` (pure Python) for HTTP.
- For packages requiring C extensions: test pip install via SSH before writing any code that depends on them. Do this in Phase 1.
- Pre-build wheels locally on a matching Python version and OS, then upload and install from the `.whl` file: `pip install ./package.whl`.
- If critical packages cannot be installed: this is a hard blocker for SiteGround and the VPS fallback must be activated.

**Detection:** Run `pip install <package>` via SSH on SiteGround and capture the full output. Any `gcc: command not found` or `fatal error: Python.h: No such file or directory` is a red flag.

**Phase to address:** Phase 1 — validate all dependency installs on actual SiteGround SSH before writing any application code.

### Pitfall 11: Corrupt or Password-Protected PDFs Crashing the Ingestion Pipeline

**What goes wrong:** A user uploads a password-protected PDF. `pypdf` raises `PdfReadError` or `NotImplementedError` for Acrobat 6+ encryption. Without exception handling, the error propagates and crashes the upload request. In the worst case, the partial document state is left in the vector store — some chunks indexed, others not.

**Why it happens:** pypdf supports only algorithm codes 1 and 2 (legacy RC4 encryption). AES-encrypted PDFs (Acrobat 6.0 and above, which is nearly all modern PDFs) are not decryptable by pypdf without the password.

**Consequences:** Upload endpoint returns 500. Admin sees no actionable error. The document appears to be uploaded (stored on disk) but is not indexed.

**Prevention:**
- Wrap all document parsing in a try/except that catches `Exception` and returns a structured error: `{"status": "failed", "reason": "PDF is password-protected or corrupt"}`.
- Validate file integrity before parsing: check PDF header (`%PDF-`) and attempt a metadata-only read before full text extraction.
- Implement transactional indexing: either all chunks for a document are committed to ChromaDB or none are. Use a staging collection or a delete-on-failure rollback.
- For password-protected PDFs: return a clear admin-facing error message. Do not silently swallow the exception.

**Detection:** During development, test the pipeline with a known password-protected PDF and a corrupt PDF (truncate a valid one). Both should produce clean error responses, not 500s.

**Phase to address:** Phase 2 (Document Ingestion) — error handling and transactional indexing should be built as part of the ingestion feature, not as a later fix.

### Pitfall 12: URL Crawl Failures on JavaScript-Rendered Pages

**What goes wrong:** Admin adds a URL for crawling. The page content is rendered client-side by React/Vue/Next.js. `requests` + `BeautifulSoup` fetches the raw HTML, which contains only `<div id="root"></div>` and no actual content. The document is indexed with essentially empty text, polluting the vector store with empty chunks.

**Why it happens:** Static HTTP clients fetch the server-rendered HTML. Modern web apps deliver a JS bundle; the actual content is injected after JS execution in the browser.

**Consequences:** Indexed "document" returns chunks that are empty or boilerplate. Retrieval may return these empty chunks, causing the LLM to say it has no relevant information even when the URL was supposed to provide it.

**Prevention:**
- Detect JS-heavy pages: if `<script>` tags outnumber `<p>` tags by 5:1 and body text is under 500 characters, flag the URL as JS-rendered.
- For v1: reject JS-rendered URLs with a clear admin error. Do not silently index an empty document.
- For v2: integrate a headless browser (Playwright) or use a scraping API (Firecrawl, Jina Reader API) that handles JS rendering.
- Always store the raw fetched text alongside the chunks for debugging — admin can verify what was actually indexed.

**Detection:** After crawling a URL, log the character count of extracted text. Any URL returning under 200 characters of body text is suspect.

**Phase to address:** Phase 2 (Document Ingestion / URL Crawl feature) — build the JS-detection check before the indexing step.

### Pitfall 13: Context Window Overflow Causing Truncated Answers or API Errors

**What goes wrong:** The prompt sent to the LLM includes the system prompt + retrieved chunks + chat history + user question. For a model with a 4096-token context window (some free models), retrieving 5 chunks of 512 tokens each (2560 tokens) + a 500-token system prompt + chat history leaves no room for the answer. The API either truncates the prompt silently or returns a `context_length_exceeded` error.

**Why it happens:** Developers set `top_k=5` and chunk size to 512 tokens without calculating the total assembled prompt size against the model's context limit.

**Consequences:** Answers are cut off mid-sentence, or the API returns an error that the application doesn't handle gracefully.

**Prevention:**
- Count tokens before sending. Use `tiktoken` or a character-based approximation (1 token ≈ 4 chars) to estimate prompt length.
- Define a budget: `max_context = model_context_window - max_output_tokens - system_prompt_tokens - chat_history_tokens`. Retrieve only as many chunks as fit within this budget.
- Prefer models with at least 8192-token context windows. On OpenRouter free tier, `mistral-7b-instruct` and `llama-3-8b-instruct` variants offer 8192–32768 tokens.
- Truncate chat history from oldest to newest if needed to stay within budget.

**Detection:** Log total estimated token count for every request. Alert when it exceeds 80% of the model's limit.

**Phase to address:** Phase 2 (RAG Pipeline / Prompt Engineering) — build the token budget calculation into the context assembly function from day one.

## Minor Pitfalls

### Pitfall 14: Passenger Process Restart Not Reflected Until tmp/restart.txt Is Touched

**What goes wrong:** Developer deploys updated code via SSH or FTP. The old Passenger process continues serving stale code because Passenger caches the application in memory and does not hot-reload on file changes.

**Why it happens:** Passenger is designed for stability — it does not watch for file changes. Restart requires an explicit signal.

**Prevention:**
- Add `touch tmp/restart.txt` to the deployment script or run it manually after every deploy.
- Create a `deploy.sh` script: `rsync files → touch tmp/restart.txt`.
- For cPanel-based deploys: the cPanel Python Selector "Restart" button also works.

**Detection:** Edit a visible response (e.g., add a version field to the `/health` endpoint) and check if it changes after code upload. If not, the old process is still running.

**Phase to address:** Phase 1 — document this in the deployment runbook before the first deploy.

### Pitfall 15: Large File Upload Blocking the Passenger Worker Thread

**What goes wrong:** A 50 MB PDF is uploaded. The Passenger worker thread is occupied reading the file, parsing it, and indexing it synchronously for the duration — which may be 30–60 seconds. During this time, all other incoming requests (including chat queries) queue behind this single worker thread. SiteGround may also enforce an upload timeout at the web server level (typically 60 seconds), killing the upload mid-process.

**Why it happens:** Synchronous ingestion in a single-threaded WSGI worker has no concurrency. The request handler blocks until the full pipeline completes.

**Prevention:**
- Set a file size limit (e.g., 20 MB) at the upload endpoint and reject larger files with a clear message.
- For larger files: accept the upload, write to disk, return a 202 Accepted, and process in the background on the next request cycle or via a simple file-queue approach.
- Configure the web server upload timeout to at least 120 seconds in `.htaccess` if possible.

**Detection:** Time the upload of a 10 MB PDF. If it takes more than 30 seconds, the synchronous approach will cause problems with the web server's timeout.

**Phase to address:** Phase 2 (Document Ingestion) — set the file size limit in the upload validation before any real documents are processed.

### Pitfall 16: Hallucination When Retrieved Context Is Irrelevant

**What goes wrong:** A user asks a question that has no answer in the document library. The retrieval step returns the top-k chunks regardless of relevance score. The LLM receives weakly-related context and generates a confident-sounding but hallucinated answer instead of saying "I don't have information about that."

**Why it happens:** ChromaDB returns the nearest neighbours regardless of actual similarity. Without a minimum similarity threshold, even very distant vectors are returned and passed to the LLM.

**Consequences:** The chatbot fabricates answers. For a consulting business, this is a brand and trust risk.

**Prevention:**
- Implement a similarity threshold: if the top-1 chunk's cosine distance exceeds a threshold (e.g., distance > 0.7 for ChromaDB's default distance metric), return a fallback response: "I don't have specific information about that in my knowledge base."
- Tune the threshold against real queries during Phase 2 testing — start conservative (high threshold = lower recall) and relax only when retrieval quality is confirmed.
- Include in the system prompt: "Answer only from the provided context. If the context does not contain the answer, say you don't know."

**Detection:** Craft 5 questions that definitely have no answer in the documents. If the chatbot answers any of them confidently, the threshold is too permissive.

**Phase to address:** Phase 2 — implement threshold gating as part of the initial retrieval function.

### Pitfall 17: Encoding Errors on DOCX or TXT Files

**What goes wrong:** A TXT or DOCX file encoded in Windows-1252 or Latin-1 (common for older business documents) is read with `open(path, 'r')` defaulting to UTF-8. Python raises `UnicodeDecodeError`, crashing the ingestion pipeline.

**Why it happens:** Python 3's default file encoding is the system locale encoding (usually UTF-8 on Linux). Older documents from Windows environments frequently use Windows code pages.

**Prevention:**
- Always read text files with explicit encoding detection: use `chardet` to detect encoding, then decode accordingly.
- Alternatively, open files with `errors='replace'` as a fallback: `open(path, 'r', encoding='utf-8', errors='replace')`. This loses some characters but never crashes.
- For DOCX: `python-docx` handles encoding internally, but validate that extracted text is not full of replacement characters (`???`).

**Detection:** Test ingestion with at least one Windows-1252-encoded file. If you don't have one, create one with Python: `open('test.txt', 'w', encoding='cp1252').write('Café résumé')`.

**Phase to address:** Phase 2 (Document Ingestion) — add encoding detection to the text file reader at initial implementation.
