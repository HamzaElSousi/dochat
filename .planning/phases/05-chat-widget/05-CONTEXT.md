# Phase 5: Chat Widget - Context

**Gathered:** 2026-05-09
**Status:** Ready for planning

<domain>
## Phase Boundary

Phase 5 delivers a vanilla JS chat widget that embeds on any website via a single `<script>` tag. Visitors can open a floating panel, type questions, and receive answers from the existing `POST /chat` endpoint — with typing indicator, follow-up question chips, and full session history within the tab. The widget renders inside Shadow DOM so host-site CSS cannot break it, is fully usable on mobile, and is themeable via `window.DocChatConfig`. No new ingestion or query logic — Phase 5 is a frontend layer on top of the existing RAG backend.

**Backend change in scope:** `POST /chat` response schema gains a `chips` field (3 follow-up questions generated by the LLM in the same call). `app/services/query.py` must be updated to parse chips from the LLM response. This is a Phase 5 responsibility.

</domain>

<decisions>
## Implementation Decisions

### Panel Visual Design (D-01 to D-04)
- **D-01:** Fixed corner panel anchored bottom-right, above the FAB. Desktop dimensions: 380×560px. On mobile (≤480px wide) the panel expands to nearly full-screen. Standard chatbot layout (not a slide-in drawer, not a floating bubble).
- **D-02:** Panel header contains: configurable logo (small, left-aligned image), title text (configurable, default "Ask us anything"), and a × close button on the right.
- **D-03:** Messages rendered as left/right aligned chat bubbles. Visitor messages: colored bubble on the right (primaryColor background). Bot answers: neutral bubble on the left (botBubbleColor background).
- **D-04:** FAB button is fixed bottom-right. Clicking opens the panel; clicking × (or FAB again) closes it. History is retained in JS state for the duration of the tab session.

### Follow-up Chips (D-05 to D-07)
- **D-05:** Chips are backend-generated. The LLM generates 3 contextually relevant follow-up questions in the same API call. Backend adds a `chips` field to the `POST /chat` response: `{"answer": "...", "session_id": "...", "fallback": false, "sources": [...], "chips": ["Q1", "Q2", "Q3"]}`.
- **D-06:** Generation strategy: structured prompt addition to the existing LLM prompt in `app/services/query.py`. The LLM is asked to output a JSON block `{"chips": ["Q1", "Q2", "Q3"]}` after its answer. The parser extracts chips from the response body.
- **D-07:** Chip click auto-sends — clicking a chip populates the input AND immediately submits the message (same as typing + pressing Enter). If LLM parsing fails or chips are absent, `chips = []` and no chips are rendered (silent fail — no error, no fallback chips).

### Session Storage (D-08 to D-09)
- **D-08:** `session_id` returned by the backend is stored in `sessionStorage` (not localStorage). Clears when the tab closes. Each new tab/page load starts a fresh session. The backend retains history for the LLM context window; the widget does not re-fetch or display prior session history on reload.
- **D-09:** Chat message history is stored in-memory (JS state) only — not serialized to sessionStorage. Navigation within the same site reloads the page and clears displayed history (though the session_id in sessionStorage allows the backend to continue the same session). History persistence across navigation is left to Claude's discretion.

### Script Delivery + DocChatConfig (D-10 to D-11)
- **D-10:** `widget.js` delivery location (Flask static route vs direct file in `public_html/dochat/`) is left to Claude's discretion based on what integrates cleanest with the CGI deployment model.
- **D-11:** `window.DocChatConfig` accepts the following properties (all optional — widget has sensible defaults):
  ```js
  window.DocChatConfig = {
    primaryColor: '#3b82f6',   // FAB background + header background default + visitor bubble
    headerBg: '#1e3a5f',       // header background (overrides primaryColor for header)
    botBubbleColor: '#f1f5f9', // bot message bubble background
    userBubbleColor: '#3b82f6',// visitor message bubble background
    textColor: '#1e293b',      // primary text color
    logo: 'https://...',       // URL to logo image shown in header
    title: 'Ask us anything',  // header title text
    apiUrl: 'https://social-automate.com/chat', // REQUIRED: POST /chat endpoint URL
    borderRadius: '12px',      // panel + bubble corner radius
    fontFamily: 'inherit',     // inherit from host page or override
  };
  ```
  All CSS variables are applied via Shadow DOM CSS custom properties so they cannot leak to the host page. `apiUrl` is effectively required — widget logs a warning and is non-functional without it.

### Claude's Discretion
- `widget.js` delivery: Flask static route at `/dochat/widget.js` vs static file in `public_html/`. Choose whichever integrates cleanest with the CGI model and `.htaccess` pattern.
- In-memory history persistence across same-tab navigation: Claude can choose whether to serialize message history to `sessionStorage` alongside `session_id` if it simplifies the implementation.
- FAB icon: standard chat bubble SVG icon (no library needed).
- Empty state (no messages yet): a welcome message or prompt text in the chat body.
- Input placeholder text default value.
- Typing indicator animation style (CSS keyframe dots).
- Error state: network error or 500 from backend — show inline error message in chat body, allow retry.
- `sessionStorage` key name for `session_id`.

</decisions>

## Existing Code Insights

### Reusable Assets
- `app/routes/chat.py → POST /chat`: Live endpoint. Request: `{message: str, session_id: str|null}`. Current response: `{answer, session_id, fallback, sources}`. Phase 5 adds `chips: [str, str, str]` to this response.
- `app/services/query.py → handle_chat()`: Core RAG function. Phase 5 modifies the LLM prompt to include chip generation and parses `{"chips": [...]}` from the LLM response body.
- `app/static/admin.js`: Existing vanilla JS fetch pattern. Reference for code style, error handling approach, and how static JS is deployed in this project.

### Established Patterns
- Vanilla JS only — no jQuery, React, Vue, or any npm dependency in the widget file
- Shadow DOM isolation: `attachShadow({mode: 'open'})` on a host element injected into `<body>`
- CSS custom properties for theming: map `DocChatConfig` values to `--dc-*` CSS variables inside the shadow root
- No local ML or heavy Python dependencies — widget talks to the Flask API only
- Manual `BEGIN`/`COMMIT`/`ROLLBACK` in all DB code (backend constraint, irrelevant to widget JS)
- All storage paths via `STORAGE_PATH` (backend constraint)

### Integration Points
- Widget → `POST /chat`: Sends `{message, session_id}`, receives `{answer, session_id, fallback, chips, sources}`. Stores returned `session_id` in `sessionStorage`.
- Widget → `fallback: true` in response: Phase 6 will use this to trigger the lead capture form. Phase 5 should render the fallback message text but NOT implement the lead form (that's Phase 6 scope).
- Phase 5 modifies `app/services/query.py` (chip generation) and `app/routes/chat.py` (response schema). Phase 6 adds a `POST /leads` route — no conflict.
- `.htaccess` needs a new RewriteRule for `widget.js` URL.

## Specific Ideas

- **DocChatConfig shape** (D-11): Full 10-property theme object covering colors, logo, title, apiUrl, borderRadius, fontFamily. All optional except `apiUrl`. Applied as CSS custom properties inside Shadow DOM.
- **Chip click behavior** (D-07): Auto-send on click (not just populate input). Silent fail on parse error.
- **Session storage key**: `sessionStorage` for `session_id`. Key name at Claude's discretion (e.g., `dochat_session_id`).
- **Mobile breakpoint**: ≤480px → panel goes full-screen. Touch targets ≥ 44px per WIDGET-06.
- **Embed snippet** (what the admin puts on their site):
  ```html
  <script>
    window.DocChatConfig = {
      apiUrl: 'https://social-automate.com/chat',
      primaryColor: '#3b82f6',
      title: 'Ask us anything'
    };

  ```
